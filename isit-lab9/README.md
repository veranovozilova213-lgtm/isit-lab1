**Лабораторная работа №9**
Интеграция компонентов веб-приложения
===

### 

### **Цель лабораторной работы**

Объединить клиентскую и серверную части веб-приложения в единую систему: подключить клиент к настоящему REST API, реализовать авторизацию с разграничением прав по ролям, пройти полный пользовательский сценарий работы и выполнить комплексное тестирование.





#### **Краткое описание выполненного задания**



Клиентское приложение из лабораторной работы №5 (HTML, CSS, JavaScript) подключено к серверу из лабораторной работы №7, а данные сервера перенесены из JSON-файлов в базу данных PostgreSQL из лабораторной работы №8. Учебный сервер `mock-api.js` отключён: на запросы клиента отвечает настоящий сервер. При первом соединении обнаружились расхождения в договорённостях между клиентом и сервером (имена полей, формат ошибок, обязательное поле курьера, параметры поиска и сортировки); они согласованы и описаны.

На сервере реализована авторизация: вход по email и паролю, выдача токена, проверка токена на всех адресах API, две роли (администратор и пользователь), выход с отзывом токена. Пароли и токены хранятся в базе только в виде хешей. Клиент получил экран входа, защиту от истёкшей сессии, интерфейс по роли и обработку ошибок сети, 401, 403 и 422. Работу проверяют автоматические тесты API и сквозные сценарии в браузере.





#### **Предметная область**



В ходе выполнения работы система была перенесена с демонстрационного примера «Система управления задачами» на предметную область «Приложение доставки заказов». Основной сущностью стали заказы, а вместо проектов курьеры. Были изменены SQL-скрипты базы данных, модели, маршруты API и формы на клиенте. Проверка работоспособности выполнена с помощью автоматических тестов API и сквозных сценариев в браузере.

#### **Как устроена интеграция**



|**Файл клиента**|**Назначение**|
|-|-|
|js/config.js|Адрес API (`API\\\_BASE`): пустой, так как клиент и API находятся на одном сервере.|
|js/api.js|Единственное место, где клиент обращается к серверу: токен и заголовки, проверка ответа (`checkResponse`). Функции: `login`, `me`, `logout`, `getProjects` (курьеры), `getTasks` (заказы), `createTask` (создать заказ), `updateTask`, `deleteTask`.|
|js/app.js|Экраны «Вход» и «Список заказов», обработчики событий, вывод таблицы, обработка ошибок (401, 403, 422, потеря связи).|

|**Файл сервера**|**Назначение**|
|-|-|
|public/index.php|Точка входа: CORS, проверка токена для всего API, кроме входа, маршрутизатор.|
|app/Core/Database.php|одключение к PostgreSQL через PDO|
|app/Models/\*Repository.php|Работа с таблицами: базовый `PgRepository` (all, find, add, update, delete) и модели заказов (`TaskRepository`), курьеров (`ProjectRepository`), участников (`UserRepository`).|
|app/Core/Auth.php|Выдача, проверка и отзыв токенов|
|app/Controllers/Api/AuthController.php|Вход: `POST /api/auth/login`, проверка: `GET /api/auth/me`, выход: `POST /api/auth/logout`.|
|app/helpers.php|Функции `bearer\\\_token()`, `require\\\_auth()`, `require\\\_role()`, `public\\\_user()`, CORS.|
|app/Controllers/Api/\*ApiController.php|Ресурсы API (заказы, курьеры, участники). Права проверяются через `require\\\_role('manager')`|
|sql/schema.sql`, `sql/seed.sql`, `bin/reset-db.php|Структура базы данных, тестовые данные и команда, которая возвращает базу к исходному состоянию.|

#### **Что пришлось согласовать между клиентом и сервером**



|**Расхождение**|**Решение**|
|-|-|
|Имена полей и даты: клиент отправлял `dueDate` и пустую строку `""`, а сервер ждет `due\\\_date` и `null`.|В `app.js` исправлено имя поля и добавлена проверка: если дата не выбрана, отправляется `null`.|
|Формат ошибок: сервер присылает ошибки полей в объекте `errors`, а клиент искал их в `fields`.|В `api.js` и `app.js` клиент переведен на чтение `errors`, поэтому красные подсказки теперь работают.|
|Параметры списка: старый формат сортировки `\\\_sort=id` и незакодированные спецсимволы в поиске.|В `api.js` клиент теперь отправляет `sort=-id` и использует `encodeURIComponent` для безопасного поиска.|
|Обязательное поле курьера:\*\* серверу нужен `project\\\_id` (номер курьера) числом, а в форме его не было.|В форму добавлен выпадающий список курьеров, его значение отправляется как `Number(...)`.|
|Обработка статусов 401 и 403: клиент показывал «ошибку сервера» вместо возврата на вход или скрытия кнопок.|В `checkResponse` добавлен перехват 401, а в `renderTasks` кнопка «Удалить» скрывается для ролей, отличных от `manager`.|

#### **Вывод**



В результате работы клиентская и серверная части объединены в единую систему доставки заказов. Клиент общается с сервером через `api.js`, а все расхождения в контракте (имена полей, формат ошибок, сортировка) были успешно устранены.

Реализована полноценная авторизация: пароли хранятся в виде хешей, доступ к API защищен токенами, а права строго разграничены по ролям (manager, developer, tester). Клиент корректно реагирует на ответы 401, 403, 422 и потерю связи.

Данные перенесены из JSON-файлов в PostgreSQL. Работа с базой построена на подготовленных запросах, что защищает систему от SQL-инъекций. 

Главный вывод: проверки в интерфейсе (например, скрытие кнопки «Удалить») нужны только для удобства, настоящая защита всегда реализуется на стороне сервера. Интеграция прошла успешно, что подтверждено 54 пройденными автотестами API.
