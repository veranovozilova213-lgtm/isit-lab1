# **Лабораторная работа №3**



#### **Проектирование архитектуры информационной системы**



**Вариант 12. Система управления доставками**



Система предназначена для управления доставкой заказов клиентам. Необходимо учитывать заказы, клиентов, адреса доставки, курьеров и статусы заказов.
Оператор должен иметь возможность назначать курьеров и отслеживать состояние доставки.





**Цель работы:**
Изучить принципы проектирования архитектуры информационных систем, определить структуру приложения, спроектировать взаимодействие между основными компонентами и подготовить структуру программного проекта для дальнейшей разработки.



**Краткое описание выполненного задания:**

На основе предметной области службы доставки заказов клиентам спроектирована архитектура информационной системы: выбран архитектурный стиль, определены компоненты и их ответственность, описано взаимодействие компонентов на примере одного сценария, разработана структура каталогов проекта, а также выделена и отражена в архитектуре индивидуальная нетиповая особенность предметной области — автоматическое уведомление клиентов и курьеров об изменении статуса доставки.



### **Основные результаты работы**





1. **Архитектурный стиль**



Выбрана трёхуровневая архитектура веб-приложения



|**Уровень**|**Назначение**|
|-|-|
|Frontend (клиентская часть)|Отображение интерфейса личных кабинетов (клиента, курьера, оператора, администратора), обработка пользовательского ввода, отправка HTTP-запросов к API для управления заказами и доставкой.|
|Backend (серверная часть)|Приём запросов от интерфейса, обеспечение безопасности, валидация данных, выполнение бизнес-логики распределения заказов, смена статусов доставки, интеграция со службами рассылки уведомлений.|
|Database (база данных)|Надежное и постоянное хранение структурированных данных о пользователях, заказах, адресах, курьерах, текущих статусах логистики и всей истории их изменений.|





**2. Компоненты системы**



|**Компонент**|**Назначение и ответственность**|
|-|-|
|Веб-интерфейс (Frontend)|Отображение форм оформления заказов, списков доступных доставок, интерактивных карт для курьеров и панелей мониторинга для операторов; отправка запросов к API.|
|API / Роутинг|Приём входящих HTTP-запросов, проверка их структуры и перенаправление на соответствующие маршруты.|
|Контроллеры|Извлечение параметров запроса (данные нового заказа, ID курьера), передача их в соответствующие сервисы бизнес-логики и формирование JSON-ответов для фронтенда.|
|Бизнес-логика|Реализация правил логистики и распределения: проверка доступности курьера, валидация адресов, расчёт загрузки персонала, перевод заказов по цепочке статусов|
|Репозитории|Изоляция работы с СУБД: выполнение оптимизированных SQL-запросов для создания, чтения, обновления и удаления записей о заказах и клиентах.|
|Модуль аутентификации|Проверка учётных данных пользователей при входе в систему и строгое разграничение прав доступа|
|Модуль уведомлений|Автоматическая сборка и отправка мгновенных Email, SMS или Push-сообщений клиентам о том, что заказ передан курьеру и курьерам о назначении новой доставки.|
|База данных|Физическое хранение таблиц: clients, couriers, operators, orders, addresses, delivery\_statuses и status\_history.|





**3. Взаимодействие компонентов**



Общая последовательность обработки запроса пользователя (мы сделали назначение заказа курьеру):



&#x20;  1. Оператор выбирает свободного курьера и нажимает кнопку «Назначить на заказ» в панели управления веб-интерфейса.

&#x20;  2. Frontend отправляет HTTP-запрос к API, передавая ID заказа и ID выбранного курьера.

&#x20;  3. API / Роутинг проверяет маркер доступа через Модуль аутентификации, подтверждает роль пользователя и передаёт запрос в соответствующий контроллер заказов.

&#x20;  4. Контроллер принимает параметры, извлекает JSON-тело запроса и вызывает метод сервиса бизнес-логики.

&#x20;  5. Сервис бизнес-логики проверяет правила системы, после чего обращается к репозиторию для обновления информации.

&#x20;  6. Репозиторий выполняет SQL-запрос к базе данных  для изменения статуса заказа на «Назначен курьер» и связывания ID курьера с записью заказа.

&#x20;  7. Сервис бизнес-логики инициирует автоматическую отправку сообщения через модуль уведомлений, который отправляет Push-уведомление назначенному курьеру в его мобильное приложение и Email-уведомление клиенту о том, что его заказ передан в доставку.

&#x20;  8. Результат операции возвращается через API обратно на Frontend, где у оператора обновляется статус в таблице, а курьер видит новый заказ в своём списке.

**5. Индивидуальная особенность предметной области**



В отличие от базовых операций по управлению данными, таких как создание карточки заказа, редактирование профилей или просмотр списков, ключевой спецификой данной системы является сквозное автоматическое информирование клиентов и курьеров о каждом этапе продвижения посылки. Эта задача не ограничивается простым обновлением строк в базе данных.

Процесс отправки сообщений полностью вынесен за рамки основного цикла обработки запроса: как только статус доставки меняется, например, заказ переходит в состояние «в пути», система мгновенно регистрирует это событие и обрабатывает его в фоновом режиме. Такой подход позволяет отправлять оповещения через внешние каналы (Push/SMS/Email), не заставляя пользователя ждать окончания отправки на экране приложения.

В структуре приложения за эту логику отвечает изолированный компонент «Модуль уведомлений». Серверные сервисы фиксируют смену статуса заказа и передают управление этому модулю, который берет на себя интеграцию с внешними сервисами рассылки. Данная цепочка шагов наглядно продемонстрирована на диаграмме взаимодействия компонентов.
